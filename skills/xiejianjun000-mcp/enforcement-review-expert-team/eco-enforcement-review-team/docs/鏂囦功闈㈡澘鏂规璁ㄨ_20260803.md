## 二、核心挑战

### 2.1 四种占位符解析

```
【提示文本】  → AI 需理解提示语义后填充，填充后删除括号内容
  □ 勾选项    → AI 需根据案件事实选择勾选/不勾选，不勾选则删除该行
  （可选）    → AI 需根据法律规定和案情判断是否填写
  _____下划线 → AI 填充具体值后删除下划线
```

### 2.2 分支逻辑

以行政处罚决定书为例，"陈述申辩"段存在 5 条分支路径：

```
有听证权 + 未陈述申辩未听证 → 选第1条
有听证权 + 未陈述申辩但要求听证 → 选第2条
有听证权 + 陈述申辩但未要求听证 → 选第3条
有听证权 + 陈述申辩且要求听证 → 选第4条
无听证权 + 未陈述申辩 → 选第5条
无听证权 + 陈述申辩 → 选第6条
```

### 2.3 输出一致性

"确保输出文本与文档保持一致"意味着：即便是AI填充后，文书的法律用语、固定句式、条款引用格式都不能变形。

## 三、技术方案对比

### 方案A：Jinja2 模板引擎

```
PDF提取 → 纯文本模板 → Jinja2变量标记 → 字段Schema JSON
                ↓
案件事实(结构化) → 填充引擎 → 渲染 → .docx输出
```

**流程**：
1. 从PDF提取74个文书为纯文本模板
2. 手动标记每个文书中的可填字段为 `{{variable}}`
3. 为每个文书写字段Schema：字段名、类型、来源（案件数据/法律检索/AI推断）、校验规则
4. 案件数据 + Jinja2 → 渲染完整文书

| 优势 | 劣势 |
|------|------|
| 格式100%精确 | 74个模板需逐一提取标记 |
| 分支逻辑天然支持（if/for） | PDF→文本转换可能丢失格式 |
| 与docx/pdf输出路径无缝衔接 | 复杂文书分支路径多，模板会变长 |
| 可版本化管理 | 字段Schema维护成本高 |

### 方案B：Skill 直调模式

```
文书 Skill（每个文书一个SKILL.md）
  ├─ 嵌入精确模板原文
  ├─ 字段映射表（案件属性→文书字段）
  ├─ 分支决策树（□选择逻辑）
  └─ 制作指南（约束条件）
```

**流程**：
1. 为每个文书创建独立Skill（74个SKILL.md）
2. 每个Skill内嵌模板原文+字段映射表
3. AI调用Skill时，读取案件数据，按映射表填充，按决策树处理分支
4. 渲染输出

| 优势 | 劣势 |
|------|------|
| 完全复用现有Skill架构 | 74个Skill维护量较大（但可批量生成） |
| AI自然语言理解字段语义 | 依赖AI的文本生成一致性 |
| 可直接嵌入制作指南作为约束 | 可能存在小概率的格式偏离 |
| 团队内的文书生成专家可直接调用 | 复杂度高的文书需要较长的SKILL.md |

### 方案C：字段Schema + 模板存储（混合方案，推荐）

```
文书面板系统
├── templates/            ← 74个精确模板（Markdown格式）
│   ├── 04_立案审批表.md
│   ├── 08_现场检查笔录.md
│   ├── 38_行政处罚决定书.md
│   └── ...
│
├── schemas/              ← 74个字段定义文件（JSON/YAML）
│   ├── 04_立案审批表.yaml
│   ├── 08_现场检查笔录.yaml
│   ├── 38_行政处罚决定书.yaml
│   └── ...
│
└── doc-panel/            ← 1个总控 Skill
    └── SKILL.md          ← 文书选择→Schema加载→数据填充→模板渲染
```

**每个 schema 文件的结构**：

```yaml
# schemas/38_行政处罚决定书.yaml
id: "38"
name: "行政处罚决定书"
category: "行政处罚·决定"
complexity: "high"
template: "templates/38_行政处罚决定书.md"

fields:
  - id: "文号年份"
    key: "{{文号年份}}"
    type: "string"
    source: "案件数据.立案年份"
    default: "当前年份"
    
  - id: "当事人名称"
    key: "{{当事人名称/姓名}}"
    type: "string"
    source: "案件数据.当事人.名称"
    required: true

  - id: "违法事实陈述"
    key: "{{违法事实陈述}}"
    type: "text"
    source: "AI推断.从案件事实生成"
    constraints:
      - "包含违法行为发生的时间、地点、情节、动机、危害后果"
      - "引用法律条文须精确到条款项"

branches:
  - id: "陈述申辩段"
    conditions:
      - if: "有听证权 AND 未陈述申辩 AND 未要求听证"
        select: "branch_1"
      - if: "有听证权 AND 未陈述申辩 AND 要求听证"
        select: "branch_2"
      # ... 6条分支
```

**流程**：

```
Stage 1: PDF → 模板提取（一次性工作）
  74个PDF页面 → pdfplumber提取文本 → 人工/半自动标记占位符 → 存储为.md模板

Stage 2: 字段Schema定义（一次性工作）
  每个模板 → 人工定义字段映射 + 分支逻辑 + 校验规则 → 存储为.yaml schema

Stage 3: 运行时自动填充（每次使用）
  案件数据 → doc-panel Skill → 加载模板+schema → 遍历字段填充
            → 处理分支逻辑 → 渲染 → .docx输出
```

| 优势 | 劣势 |
|------|------|
| 模板与逻辑分离，修改互不影响 | 74份模板 + 74份schema初始工作量较大 |
| 字段Schema可做严格校验 | 复杂分支需手写条件逻辑 |
| 模板文本100%精确（原文复制） | — |
| AI只负责"从案件数据中提取字段值"，不负责生成文本 | — |
| 可渐进式建设（先做核心15个文书） | — |

### 方案D：AI-native 语义填充

不存精确模板，仅存文书骨架描述。AI阅读制作指南后，直接从案件数据生成文书全文。

| 优势 | 劣势 |
|------|------|
| 零模板维护 | 输出格式不可控，无法100%保证一致 |
| 任何新文书即插即用 | 法律文书格式要求严格，不够用 |

**结论：方案D不适合本案场景。**

## 五、文书面板产品形态

最终交付为一个 **doc-panel Skill + 模板库**，挂在文书生成专家（文书成）名下：

```
文书成 (doc-generator)
├── doc-verification   → 现场监察记录生成
├── doc-checklist      → 核查清单生成
├── doc-report         → 评查报告生成
└── doc-panel  🆕      → 文书面板（74文书模板库+自动填充）
    ├── templates/     → 74个精确模板
    └── schemas/       → 74个字段定义+校验规则
```

**调用方式**：

```
调度官 → 文书成: "生成赢湖矿产品案的行政处罚决定书"
         │
         └─ doc-panel: 
              ├─ 加载 templates/38_行政处罚决定书.md
              ├─ 加载 schemas/38_行政处罚决定书.yaml
              ├─ 从案件数据中提取: 当事人信息、违法事实、证据、裁量、告知、听证
              ├─ 处理分支: 有听证权 + 陈述申辩 + 未要求听证 → 选branch_3
              ├─ 渲染: 替换50+占位符
              └─ 输出: .docx（保留格式，可继续编辑）
```

## 六、待讨论的开放问题

1. **模板提取方式**：手动复制 vs 脚本批量提取？PDF→文本的精度是否够用？（建议：核心15个手动核实，其余脚本辅助）
2. **字段Schema粒度**：字段拆到多细？比如"违法事实陈述"是一个大文本字段还是拆成时间/地点/行为/后果四个小字段？（建议：整体大字段+AI生成，关键字段独立校验）
3. **输出格式**：.docx（可编辑）还是纯文本？（建议：.docx，利用 docx 插件的修订痕迹功能）
4. **与现有 gen_checklist.js 的关系**：是替代还是互补？（建议：互补——gen_checklist 生成专项核查类文书，doc-panel 生成官方范本类文书）
5. **74个模板的维护**：法典08-15施行后，涉及法条引用的文书需要更新？（建议：模板中的法条用变量 `{{适用法条}}` 而非硬编码，由 legal-search Skill 动态提供）
