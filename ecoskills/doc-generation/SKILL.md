# /doc — 规范文档生成

按全局「文档生成规范」生成一篇 Markdown 文档：自动在当前项目下新建或复用 `docs/` 文件夹，文件名格式 `yyyy_MM_dd_HH_<文档名>.md`。

## 用法

用户消息中 `/doc` 之后的文本（如「订单系统开发实施计划」），或用户直接说明的文档类型/标题，即本次要生成的文档类型/标题。若未提供参数，先询问用户要生成哪一类文档再继续。

示例：
- /doc 订单系统开发实施计划
- /doc 用户中心项目架构计划
- /doc 支付上游接口说明文档
- /doc 回归测试计划
- /doc 生产环境部署说明文档

## 流程

1. **取时间戳**（必须取真实时间，禁止编造或估算）：
   - Windows/PowerShell：执行 `Get-Date -Format 'yyyy_MM_dd_HH'`（例如得到 `2026_06_25_17`）。
   - POSIX shell：执行 `date +"%Y_%m_%d_%H"`。
2. **确定文档名**：以用户给出的标题为文档名，必要时润色为标准类型之一——`开发实施计划 / 项目架构计划 / 上游接口说明文档 / 测试计划 / 部署说明文档 / 需求说明文档`。去掉空格与特殊符号（中文字符可保留）。
3. **确定路径**：`<项目根>/docs/<时间戳>_<文档名>.md`。若 `docs/` 不存在则创建。
4. **生成内容**：用 write 工具写一篇结构完整的 Markdown——
   - 顶部一级标题（与文件名一致或更完整）
   - 紧接一行元信息（日期 / 作者占位 / 版本）
   - 正文按该文档类型的合理章节展开（接口文档含字段表、测试计划含用例矩阵、部署文档含步骤与环境变量等）
5. **收尾**：在回复中给出最终文件的**绝对路径**，并简述包含的章节，方便用户定位。
6. **落盘前兜底检查（仅在回复中提示，不写入文档）**：按文档类型，从下方「检查项清单」挑对应的几条，在回复末尾以一句话列出，供用户自查是否有思考遗漏。这是**兜底提醒，不是强制章节**——文档正文保持干净，不因此增删结构。

## 检查项清单（类型感知 · 仅提示不落盘）

识别当前文档属于哪一类，取对应的 3-4 条，在回复里以「落盘前可再确认：…」的形式简短列出即可。类型判断不到时，按最接近的一类处理，或跳过本步。

| 文档类型 | 落盘前可再确认 |
|----------|----------------|
| 开发实施计划 | ① 前置依赖是否列全 ② 是否有回滚/撤销方案 ③ 验收标准是否可判定 ④ 任务是否带执行顺序 |
| 变更说明 | ① 变更是否可逆/可回滚 ② 是否已排查其他引用该处的位置 ③ 是否需同步更新测试 |
| 需求说明文档 | ① 非目标/范围边界是否写明 ② 边界与异常条件是否覆盖 ③ 术语是否一致 |
| 调查/分析报告 | ① 是否结论先行 ② 证据是否可复现（含文件/行号/数据） ③ 是否订正了先前的错误假设 |
| 上游接口说明文档 | ① 错误码是否齐全 ② 鉴权方式是否说明 ③ 字段（请求/响应）是否完整 |
| 测试计划 | ① 用例矩阵是否覆盖主流程 ② 边界/异常用例是否包含 ③ 预期结果是否明确 |
| 架构计划 | ① 关键技术选型是否给出理由 ② 组件边界与数据流是否清晰 ③ 重大取舍是否记录 |

## 与规划/讨论叠加

斜杠调用与普通会话共享同一上下文，可串联使用：

- 若当前会话上下文里已有规划、需求讨论、架构分析、接口梳理等产出的内容，**直接将其整理、补全元信息后落盘**，不要丢弃已有内容另起炉灶重新生成（「固化而非重写」）。
- 文件名与路径仍走全局规范（`docs/yyyy_MM_dd_HH_<文档名>.md`），时间戳当场用系统命令重新取。
- 常见组合：
  - 结构化计划 → /doc XXX开发实施计划
  - 架构讨论 → /doc XXX项目架构计划
  - 接口梳理 → /doc XXX上游接口说明文档
  - 用例讨论 → /doc XXX测试计划

## 注意

- **例外文件**保持原位，不进 `docs/`：`README.md`、`CHANGELOG.md`、`LICENSE`、`CONTRIBUTING.md`、代码内联注释；若项目已有框架自带的 `docs/` 目录，则复用而非覆盖其原有内容。
- 同一小时生成多篇文档时，时间戳相同，靠文档名区分即可。
- 默认输出 Markdown（`.md`）；仅当用户明确要求 Word / PDF / Excel 时才改用其他格式。
- 每次生成都要重新执行系统命令取时间戳，不要复用旧值。
